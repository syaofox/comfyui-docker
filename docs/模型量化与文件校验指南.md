# 模型量化与文件校验指南（Starnodes Converter 实战）

> 适用场景：用 `comfyui-starnodes-modelconverter` 做 fp8 / int8_convrot / int4_convrot 等量化；
> 量化或转换后出图异常（噪声、色块）的排查；大模型 safetensors 下载损坏的检测与修复。
> 本文以 Qwen-Image / Qwen-Rapid-AIO 为实例，方法对 Wan / Flux 等同样适用。

---

## 一、Starnodes Model Converter 使用要点

### 1.1 `model_type` 与 `target_format` 是两回事

- `model_type` = **层保护配置**（blacklist、fp8_layers 等），决定哪些层不量化 / 用 fp8；
  真正决定量化格式的是 `target_format`。
- 量化为 `int8_convrot` 时：`model_type` 选普通架构 profile（如 `Qwen-Image`），
  **不要**选 `Qwen-Image W4A8`——它是给 `target_format=w4a8_convrot` 用的：
  - 它多出的 `w4a8_blacklist` / `w4a8_keep_fp16` 只在 w4a8 目标下被读取（`is_w4a8` 分支）；
  - 但它的主 `blacklist` 会额外把 `txt_mod` / `img_mod` 留在 bf16，是 4bit 的保护策略，
    int8 下没必要（文件更大、偏离官方 recipe）。

### 1.2 复刻官方量化 recipe（Pro 节点 + profile）

`Star Model Layers Info` 可以从一个已验证的官方量化模型（如 Comfy-Org 的
`qwen_image_edit_2511_int8_convrot.safetensors`）提取 profile（层 → 格式），
再用 `StarUltimateModelConverterPro` 套到同架构模型上：

- `use_blacklist=no`：当 profile 已覆盖全部张量（本例 1934 个张量一一对应）时，
  关闭 models.json 黑名单可 100% 复刻官方层选择（否则 `img_mod.1` 会被强制留 bf16）。
- profile 中官方 `.comfy_quant` 生成的标签形如 `INT8_CONVROT (GS:256)`，
  Pro 转换器只精确匹配 `INT8_CONVROT`，**必须打下面的补丁**，否则静默不量化。

### 1.3 本地补丁（`custom_nodes/comfyui-starnodes-modelconverter/star_model_converter_pro.py`）

上游 main 未修复，节点被 `.update` 升级覆盖后需重新应用（`git diff` 可取回）：

| 行 | 改动 | 原因 |
|---|---|---|
| :351 | `profile_format_clean = profile_format.split("+")[0].split("_SCALE")[0].split("(")[0].strip()` | 让 `INT8_CONVROT (GS:256)`、`INT4_CONVROT (GS:.. QGS:..)`、`NVFP4 (GS:..)` 能被 Rule 4 匹配；否则落入默认分支"原样保留"，输出名却是 int8 |
| :291 | `os.makedirs(os.path.dirname(output_path), exist_ok=True)` | 输出路径带下拉框的子目录（如 `qwen/...`）时，目录不存在会报 `I/O error ... .tmpXXXX` |
| :326 | 保存后、重新加载之前 `del model_sd, new_sd` | 20GB 级模型在 16G 内存机器上加载输出时易 OOM |

**判断补丁是否生效**：日志出现 839 行 `💎 INT8_CONVROT: ...`；若全是
`kept_default` / 没有任何 `💎` 行，就是标签没匹配上。

### 1.4 输出路径规则

| 节点 / 模式 | 输出目录 |
|---|---|
| Pro | `get_folder_paths("diffusion_models")[0]`（= `models/unet`）+ 下拉框相对路径 |
| 基础版 `mode=Checkpoint`（从 AIO 提取） | `diffusion_models_dir()`：优先 basename= `diffusion_models` 的路径 |
| 基础版 `mode=Diffusion Model` | 源文件同目录（源在只读 `models-ext` 时会失败） |

AIO 内嵌模型前缀是 `model.diffusion_model.`（不是 `model.`），基础版
`AIO_MODEL_PREFIX = "model.diffusion_model."` 已匹配。

## 二、量化正确性验证（每次转换后必做）

用 `comfy_kitchen` 逐层反量化，与源权重比相对误差（本次案例 839 层，均值 0.88%、最大 1.1%）：

```python
# 在容器内执行：docker exec -i comfyui-docker python3 - <<'EOF' ...
import torch
from safetensors import safe_open
from comfy_kitchen.tensor import TensorWiseINT8Layout as L

q = out.get_tensor(k)                              # I8
sc = out.get_tensor(k[:-7] + ".weight_scale").float().cuda()
p = L.Params(scale=sc, orig_dtype=torch.bfloat16,
             orig_shape=tuple(q.shape), convrot=True, convrot_groupsize=256)
d = L.dequantize(q.cuda(), p).cpu()
err = ((d.float() - w.float()).norm() / w.float().norm()).item()
```

正常 int8 convrot 误差 ~0.9%；**>0.3 就说明量化或源有问题**。
同时检查输出 header：`weight` I8 + `weight_scale` F32 `[out,1]` +
`_quantization_metadata`（`format=int8_tensorwise, convrot=true, convrot_groupsize=256`）。

加载链路（ComfyUI 侧，便于排查）：`comfy/utils.py:convert_old_quants` 把 header
`_quantization_metadata` 注入为每层 `.comfy_quant`（`comfy/utils.py:1434`
`detect_layer_quantization` 据此开启 mixed ops），`comfy/ops.py:_load_quantized_module`
读取 `convrot` 参数，运行时走 `comfy_kitchen` 的 `int8_linear(convrot=True)`。

## 四、大模型文件完整性校验（本次的教训）

### 4.1 症状

模型输出纯噪声，但：拆分逐字节一致、量化逐层验证正确、加载无警告。
此时要怀疑**模型文件本身在下载时损坏**。

### 4.2 用 HF 官方哈希校验

HF API 的 `lfs.oid` 就是文件 sha256：

```bash
curl -s https://huggingface.co/api/models/<repo>/tree/main/<dir>
# 对比本地：sha256sum model.safetensors
```

本次案例：文件大小与官方完全一致（28,431,844,103），但 sha256 不同 → 损坏。

### 4.3 用 HTTP Range + safetensors header 定位损坏（无需重下全量）

1. safetensors header 含每个张量的 `data_offsets`；**数据区起点 = `8 + header_len`**。
2. 从 HF `Range: bytes=s..e` 拉取同一张量的对应区间（记得换算数据区起点偏移）。
3. 损坏特征（区分于模型差异）：
   - **逐值 ~98% 不同 + 排序后数值集合 99.9% 相同 + std 一致** → 数据被乱序/写错，
     典型的多线程下载器分块错乱；
   - 抽样几个大张量（如 `attn.to_q.weight`，每 block 一个）即可画出损坏 block 分布。
4. 本例损坏分布：attn.to_q 完好的 block = 0,2,6–28,54,56,58，损坏 = 4、30–52（奇数 block 亦中招）。

### 4.4 修复下载

```bash
# aria2c 多线程 + 断点续传；必须 setsid 脱离会话，否则 shell 超时会杀掉前台进程
setsid nohup aria2c -x 8 -s 8 -k 1M -c --file-allocation=none --retry-wait=5 -m 30 \
  -d <目标目录> -o <文件>.part \
  "https://hf-mirror.com/<repo>/resolve/main/<path>" > /tmp/aria2.log 2>&1 < /dev/null &
# 完成后必须：sha256sum 校验 == HF lfs.oid，再改名去掉 .part
```

- hf-mirror 会 302 回 huggingface CDN，校验仍以官方 sha256 为准。
- **坏文件不要删**，改名加 `.corrupt-<sha前8位>.safetensors` 便于对照与避免误用；
  同时把当时基于它产生的拆分/量化文件一并清理或改名。

### 4.5 流式拆分 safetensors（零内存占用，推荐）

内置 Splitter 用 `comfy.utils.load_torch_file` 全量载入内存（20GB+ 机器压力大）。
自己写**流式拆分**更稳：读 header → 过滤并去掉 `model.diffusion_model.` 前缀 →
重排 `data_offsets` → 逐张量 `seek+copy` 原文件字节。20.4GB 约 11 秒，内存 O(header)。

要点：
- 数据区起点 `data0 = 8 + header_len`；新 header 用紧凑 JSON 并补空格到 8 字节对齐
  （`(-len(body)) % 8`）；
- 写完后抽样对比源文件张量（`torch.equal`）验证；
- 产物 metadata 为空，与节点 Splitter 产物等价（本次 1934/1934 张量字节一致）。

## 五、本项目环境速查

- 容器：`comfyui-docker`；内置模型 `/mnt/github/comfyui-docker/models` ↔ 容器
  `/home/comfy/app/models`；第二块盘 `/home/syaofox/comfymodels` 只读挂到
  `/home/comfy/app/models-ext`（要写输出请用内置 models 目录）。
- `get_folder_paths("diffusion_models")` 顺序 = `models/unet` → `models/diffusion_models`
  （两者都注册，都会扫描）；`get_full_path` 按序解析，**同名文件内置优先**。
- 模型下拉框用相对路径（含子目录），转换输出会带上这个子目录。
- 改完自定义节点 Python 代码必须 `docker restart comfyui-docker` 才生效；
  容器内代码路径与宿主机 `custom_nodes/` 是同一个 volume。
- Qwen-Image 配套：TE 用 `qwen_2.5_vl_7b_fp8_scaled.safetensors`
  （`CLIPLoader`，type=`qwen_image`），VAE 用 `qwen_image_vae.safetensors`；
  Phr00t Rapid AIO 内嵌 VAE 与标准 VAE 是同一文件（md5 相同），拆出来的也能直接用。
- 内存：本机 15G RAM + 大 swap，20GB 级模型转换/拆分建议先
  `docker restart comfyui-docker` 释放常驻缓存，磁盘预留 ≥2 倍文件大小。
- 校验 VAE/TE 是否等价：小文件直接 `md5sum` 对比；TE 注意存储格式差异
  （raw fp8 vs Comfy-Org scaled fp8），同架构即可互换。

## 六、真实案例复盘：Qwen-Rapid-AIO v18 → int8_convrot

1. 目标：把 `Qwen-Rapid-AIO-NSFW-v18.safetensors`（fp8 AIO）转成 int8 convrot。
2. 用官方 2511 int8_convrot 提取 profile，Pro 节点（`use_blacklist=no`）转换成功；
   逐层反量化验证误差正常，但**出图全是噪声**。
3. 控制变量测试：官方 2511 模型正常；源 fp8、我们转的 int8、原始 AIO 经
   `CheckpointLoaderSimple` 全部噪声 → 排除转换、拆分、采样器、LoRA。
4. 文件校验：拆分与 AIO 1934 张量逐字节一致；但 AIO 的 sha256 与 HF 官方不符，
   且数据区多个张量"数值集合相同、逐值 98% 不同" → **下载分块乱序损坏**。
5. 修复：aria2c 重下 + sha256 校验通过 → 流式拆分 → 重新 int8 convrot 转换 →
   同工作流出图正常。
6. 教训：**拿到大模型先核对 HF 官方 sha256**；出现无法解释的噪声时，优先怀疑文件本身。
